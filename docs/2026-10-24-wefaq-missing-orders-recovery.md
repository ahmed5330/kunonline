# وفاق — استعادة طلبات Easy Orders غير المتزامنة (23–24 أكتوبر 2026)

**الحالة:** تعليمات تشغيل مرشحة للمراجعة وليست إثبات تنفيذ. **لم يتم فحص طلبات وفاق الفعلية أو استيرادها.**
هذه العملية منفصلة عن PR #209 الخاص بالجلسات وPR #229 الخاص بأندرويد.

## شروط لا يجوز تجاوزها
1. تحديد clientId وstoreId وconnectionId الخاصين بوفاق من بيئة كن أونلاين الحية **بعد** التحقق من أن حساب وفاق هو نفسه اتصال Easy Orders المتأثر، لا بالاستنتاج من الصحة العامة (2 متصل / 1 خطأ).
2. دخول مصرح به إلى GitHub environment `preview` أو Cloudflare control plane بقراءة فقط؛ توثيق إصدار `kunonline` و`kunonline-preview` و`kunonline-sync-preview`، الـCron، الـD1 الفعلي وربط `PREVIEW_APP` و`APP_SYNC`. لا تعتقد أن Worker HTTP 200 يُثبت تنفيذ Cron.
3. أخذ نسخة احتياطية موثقة من قاعدة D1 التي تحفظ **الطلبات الحقيقية**، والتحقق من إمكانية استعادتها قبل أول كتابة.
4. التحقق من فرع الاسترجاع #226 ثم فرع فحص الفجوات #230 ثم فرع استرجاع النواقص #231، مع اختبار Sandbox معزول عن أي مستخدم حقيقي، والتحقق من توافق المهاجرات. لا دمج في `develop` أو `main` لمجرد نجاح الاختبارات.

## 1. حصر الطلبات الناقصة (قراءة فقط)
- قارن طلبات Easy Orders لمتجر وفاق من **23 أكتوبر 2026** وما بعده مع طلبات كن أونلاين في نفس المتجر، مستخدمًا External Order ID + Short ID + معرف المتجر الخارجي الموثق.
- لا تستنتج أن كل الـ666 طلبًا المعروضة في التطبيق ناقصة، ولا أن الـ1 اتصال المتعطل هو وفاق حتى تتأكد.
- افحص تاريخ آخر webhook وآخر Short ID معروف وخطأ Cron/المزود ورموز HTTP داخليًا، دون نسخ أسرار أو أرقام العملاء إلى التقارير العامة.
- غطِّ النطاقات التاريخية حتى لو كانت خارج `lookback=80` ولا تعِد تعيين المؤشر العام.

**بعد نشر الـSandbox والتحقق من الصلاحيات** يمكن للمسؤول استخدام:
`POST /api/commerce/order-sync/audit-gaps` مع هوية مخوّلة `orders.read`:

```json
{
  "clientId": "<verified-wefaq-client-id>",
  "storeId": "<verified-wefaq-kun-store-id>",
  "connectionId": "<verified-easyorders-connection-id>",
  "fromShortId": 1000,
  "toShortId": 1029
}
```

**1000–1029 مثال اصطناعي فقط، وليس أرقام وفاق.** نطاق لا يزيد عن 30 معرفًا/طلبًا في كل فحص، وفحوص أخرى للنطاق التالي. الناتج يميز:
- `alreadyInKun`: موجود بالفعل (لا إعادة استيراد)
- `missingInKun` و `gaps[]`: موجود في المصدر وليس في المتجر المستهدف
- `missingAtProvider`: غير موجود أصلًا في Easy Orders
- `foreignStoreSkipped`: متجر خارجي آخر
- `ambiguousLegacyOrders`: سجلات قديمة غير مربوطة بمتجر، تتطلب مراجعة يدوية
- عند `rate_limited` أو `provider_error` يُستخدم `nextShortId` لإعادة محاولة نفس المعرف، وليس تخطيه.

**لا يوجد أي D1 UPDATE أو webhook POST في هذا الفحص.**

## 2. الاسترجاع الانتقائي (بعد موافقة تشغيل منفصلة)
بعد حصر أرقام `gaps[]` ومقارنتها مع مرجع المتجر والنسخة الاحتياطية، يجب على المشغّل مراجعة بيانات التكوين ورفع علم التشغيل **مؤقتًا** في البيئة الصحيحة:
`EASYORDERS_TARGETED_RECOVERY_ENABLED=true`

لا يمكن لتطبيق العميل أو طلب HTTP وحده تفعيل العلم؛ القيمة الافتراضية للعلم غير فعالة. صلاحية `orders.write` وحدها غير كافية لتنفيذ الاسترجاع: مطلوب دور إدارة المنصة أيضًا.

استخدم `POST /api/commerce/order-sync/recover-gaps` مع `orders.write` ودور `admin` في كن أونلاين ومعرف متجر مطابق، في دفعات لا تزيد عن 10 Short IDs:

```json
{
  "clientId": "<verified-wefaq-client-id>",
  "storeId": "<verified-wefaq-kun-store-id>",
  "connectionId": "<verified-easyorders-connection-id>",
  "confirmStoreId": "<verified-wefaq-kun-store-id>",
  "confirmBackup": true,
  "shortIds": [1001, 1007]
}
```

**الأرقام اصطناعية.** الحقل `confirmBackup` إقرار من المشغّل، وليس دليلًا آليًا على نسخة احتياطية: يجب إثبات النسخة بشكل مستقل قبل تشغيل العلم.

الاستيراد يعمل بوضع **Create-only** الذري: إن وصل Webhook بالتزامن مع الاسترجاع فلا تُعاد كتابة الحالة أو الملاحظات أو سجل المكالمات أو التاريخ الخاص بالطلب الموجود. ويتجاوز الطلبات الموجودة والهوية الخارجية غير المطابقة والسجلات القديمة الغامضة. يستخدم نفس معالجة Webhook الرسمية مع مراعاة عزل كل متجر، ولا يغيّر مؤشر الاسترجاع التلقائي المشترك. عند فشل رسوم الإدارة، يترك الطلب المسترجع محفوظًا ويُظهر `feeFailures` بدل الادعاء بالنجاح.

## 3. إثبات اكتمال استرجاع وفاق
1. إثبات `missingInKun=0` بعد إعادة تدقيق **كامل النطاق المطلوب**، مع حل كل `ambiguousLegacyOrders` يدويًا.
2. تطابق IDs وحالات الطلبات بالضبط بين Easy Orders وD1 والمتصفح وخدمة العملاء والطباعة وAndroid، لكل متجر وفق صلاحياته.
3. لا ازدواجية IDs أو تغيير حالات الطلبات المؤكدة/المشحونة/المحصلة، وعدم المساس بأرصدة المحافظ.
4. اختبارات التكرار (نفس الطلب لا يُستورد مرة أخرى)، حالات 429/503، رسوم الإدارة، ومراجعة جلسة صلاحيات الموظفين متعددة المتاجر.
5. إرجاع علم `EASYORDERS_TARGETED_RECOVERY_ENABLED` إلى وضعه المعطّل بعد انتهاء العملية. ومتابعة تشغيل Cron الدوري الحقيقي وعدم حدوث فجوات جديدة.
6. إذا فشلت مراقبة الإصدار، أوقف الاسترجاع وارجع للإصدار السابق من Worker فقط، **ولا تعكس بيانات طلبات العملاء الحية عشوائيًا**.
